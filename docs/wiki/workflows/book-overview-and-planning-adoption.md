# 书籍概览与规划采用工作流

## 背景

作者需要先看懂一本书缺什么，再逐层安排故事、卷、章节和场景。底层虽然采用资料与版本模型，界面必须表现为进度概览、树形目录和创作表单，不能要求作者理解数据库对象。

## 长期规则

书籍概览是正本的只读投影，不保存第二份进度真相。资料准备度、规划数、正文数、待确认事实、待结算变化、质量问题、失效项和任务状态都应从所属账本读取，并带来源与更新时间。无法确认的数据保持未知。

规划使用稳定对象和不可变版本。每个故事、卷、章节或场景节点可以有多份候选，但只有唯一采用指针。事件安排、人物弧和伏笔只是计划内容或精确资料引用，不形成另一棵树。

> 🏠 **白话比喻**：概览像机场航班屏，只汇总各航空公司的真实状态；规划候选像飞行计划草案，塔台只执行明确批准的一版。对应到系统：概览不能自行写进度，后续生产只能读取采用版本。

> 🧠 **速记方法**：**一处正本，多份候选，一个采用，精确交接。**

## 采用链

1. 建立故事总览候选并采用。
2. 卷计划记录所依据的故事版本，检查后采用。
3. 章节计划记录所依据的卷版本，并绑定稳定章节资料。
4. 场景计划记录所依据的章节版本。
5. F3 按章节资料 ID 读取当前采用章计划、父级卷版本、内容哈希和精确资料引用。

父级换版后，下游不能自动改写。旧依据产生的子计划和派生内容进入待复核，历史继续可查。回退是一次新的采用动作，而不是删除新版本。

## 计划与事实的边界

“预期受伤”“道具易主”“伏笔回收”等字段只是创作意图。正文形成后，事实与状态仍需通过证据、提案和确认流程落账。规划切版不能切换正文，正文修正规划也只能新增候选。

## 并发与恢复

所有修改携带预期修订和幂等键。冲突返回服务器修订，客户端保留本地输入；重试相同请求读取既有结果。规划只归档，不物理删除；恢复树节点必须从上级到下级进行。

## 跨机器边界

SQL 与数据字典随 Git 同步，作者填写的计划、版本、采用和引用随 PostgreSQL 逻辑备份同步。复制运行中的数据库目录不属于可接受的迁移方式。

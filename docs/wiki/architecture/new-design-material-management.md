# 新设计资料组织与安全归档边界

## Background

作者需要按类型、标签、目录和自定义条件查看同一批小说资料，但底层不能因为多种入口而复制内容。资料归档还会影响表单组合、正典事实、状态、时间、规划和派生索引，因此不能退化为直接更新状态的单步按钮。

## Decision

`cards/card_versions` 继续是资料内容唯一正本。标签和分组只保存带不可变版本的组织引用；智能视图只保存安全查询定义；六个基础书籍视图通过兼容指针进入同一视图版本模型。组织项归档永不级联归档或删除资料。

> 🏠 **白话比喻**：原稿放在一个档案柜里，标签、目录卡和检索条件只是三种找法。对应到系统：所有入口最终指向同一个 card id，不保存第二份 values。

资料归档采用“预览—确认”两阶段：先冻结所有已知反向引用、修订号和哈希，再用短期令牌确认；确认前重新计算，任何变化都拒绝旧预览。归档／恢复只追加资料版本和审计事件，并调用 026 失效传播；030、AGE 和 pgvector 仍由各自既有运行链负责。

## Current Rule

- 书籍空间与公共资源空间必须严格隔离，不能同时或都不指定。
- 分组每项一个父项，服务端拒绝自指、环路、跨书／跨空间和归档父项；资料允许多分组。
- 筛选 AST 只接受白名单字段、白名单运算符和参数值，并限制深度、条件数、排序数、游标和返回量。
- 智能视图改动不使小说事实失效；标签／分组成员作为可回源上下文资源登记，资料内容变化才沿 026 传播。
- 所有“删除”语义在当前模型中都是软归档或结束引用，不执行物理删除。
- 未接账户权限前仍记录操作人和可见性，后续权限层不得改变稳定对象或历史版本身份。

## Failure Modes

- 不要把智能视图结果存成快照；否则同一资料会出现两个真相。
- 不要接受客户端 SQL、JSONPath、Cypher 或可执行函数；即使页面只生成安全条件，服务端也必须独立校验。
- 不要仅凭预览 id 归档；必须同时校验令牌哈希、快照哈希、预期修订和实时重算结果。
- 不要在资料管理模块直接修 AGE 或向量；应通过 026/030 的既有依赖与重建链。
- 不要把公共资源 `spaceId` 当成书籍 `bookId`；二者共享组件，不共享数据边界。

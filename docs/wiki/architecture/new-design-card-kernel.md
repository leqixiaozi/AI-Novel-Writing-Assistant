# 新设计卡片内核边界

## 背景

旧小说系统已经承载稳定的页面、编辑流程和 SQLite 数据。新增创作对象如果继续扩张旧专用模型，会让字段、页面和迁移彼此绑定；但直接替换旧系统又会破坏已有作品和工作流。

## 决策

采用“旧外壳保留、新内核隔离”的渐进路线：

- 旧菜单、页面、服务和 SQLite 继续作为原业务正本。
- 所有新增卡片能力放在仓库顶层 `new-design/`，只通过公开客户端组件和 Express Router 挂载到旧外壳。
- 新接口只能出现在 `/api/new-design`。
- 新数据只写入 PostgreSQL `new_design` schema，不读取旧 SQLite，不双写，也不提供模拟持久化回退。
- 桌面发行携带版本锁定的 PostgreSQL Windows x64 运行文件；数据目录位于安装目录之外。

可以把它理解成商场保留原营业区，同时开设有独立仓库和账本的新区域：顾客仍从同一个大门进入，但新区域不能借用旧仓库的货架编号冒充自己的库存。对应到代码里，菜单和路由只是入口桥接，数据模型、校验和持久化均由 `new-design/` 自己拥有。

## 当前规则

第一阶段的最小对象边界是 `CardSpace`、`CardType`、`CardTypeVersion`、`Card` 和 `CardVersion`：

- 类型字段先保存为可编辑草稿，发布后形成不可变版本。
- 已发布结构只能增加非必填字段，不能删除或修改稳定字段。
- 卡片始终按当前已发布类型校验，未知字段、缺失必填项和错误类型会被拒绝。
- 卡片写入使用 `revision` 防止并发覆盖；每次有效状态变化保存完整快照。
- 归档只改变状态，恢复沿用原 ID 和版本历史。
- 系统目录固定提供 19 类通用小说卡片；仙侠境界、灵根、宗门等题材概念通过模板字段扩展，不增加底层专用表。
- 类型通过七种 `semantic_capabilities` 声明可参与的组合流程；动态字段继续决定实际填写内容。
- 秘密、线索、伏笔和悬念保持独立语义，目标、冲突、剧情线、事件、场景、剧情节点和弧线也不得混用。
- 关系、临时状态、字典项、正文版本、AI 评价、任务日志、时间线和关系图不建成核心卡片，由后续关系、挂载、版本和视图层承载。
- 稳定字典项、关系类型和真实卡片关系进入独立表；关系具备方向、允许源/目标类型、数量、状态、作用域和属性。
- 卡片组表单以不可变版本发布；预览和实际填写读取同一份定义，旧实例继续引用创建时的版本。
- 挂载局部字段只描述某张卡片在当前组合里的用途，不复制或改写来源卡片。
- 每本书是独立聚合根与独立 `CardSpace`，安装模板时复制类型、字典、关系、表单和种子卡片快照。
- 书内类型允许独立调整名称、说明、分组、默认值和选项显示，但稳定字段键、数据类型和兼容性约束仍受保护。
- 模板升级只追加新的非必填稳定字段；删除、修改、同键冲突和必填新增只报告，不覆盖书内定制。
- 书内基础维护使用章节、线索／伏笔、角色、事件／时间、世界和资源六种视图；视图共享同一选中对象和资料检查器，不拥有事实副本。
- 故事时间、叙事章节和正文锚点分别由 `story_time_positions`、`narrative_placements`、`text_anchors` 管理；人物双方通过一条 `card_relations` 显示正反称谓。
- `book_view_configs` 只允许保存布局、筛选、分组、排序、显示、展开状态和默认范围，并随模板快照安装。
- 普通卡片字段保持即时保存；故事时间、叙事章节、人物关系和伏笔锚点必须先生成 `book_change_sets` 影响预览，再以单个事务统一应用。预览后修订号变化时整批拒绝。
- 市场扫描、市场分析、拆书和稿件诊断共用版本化研究底座；来源原文、运行输入、提示词、模型、预算、结果、证据与候选采用都各自留痕。
- 研究重跑必须新增运行版本，参考包发布与书籍采用必须锁定精确版本；新结果不能覆盖旧报告，也不能自动创建书籍或正式卡片。
- 市场榜单适配器只返回公开作品元数据，逐来源隔离成功与失败；市场 AI 分析必须由用户在圈选具体条目后显式启动，输出先进入候选采用事务。
- 拆书运行必须先锁定真实文本版本、用途、范围、预算和由当前发布规格编译出的分析计划；八维报告、证据和候选绑定运行版本，参考学习只抽象方法，稿件诊断不生成候选。
- 研究 AI 候选生成后立即持久化为待处理提案，并以不可变版本记录用户采用前的修改；它仍不是正式事实。新建、合并、保存资源、仅作参考和忽略都由作者明确触发；正式写入必须在同一事务中留下采用记录和字段来源，合并同时检查目标资料修订号。
- 状态结算能力按书籍空间的类型、字段、关系和关系维度配置；人物、组织、道具、地点与轻量生命周期对象使用不同默认策略，世界、策略和参考资料默认不参与。
- 初始状态和章节变化都是只追加历史；AI 只能创建变化提案，只有当前采用正文且用户明确确认后才能生成章节结算和有效状态流水。
- 当前状态是可重建投影，不是独立事实正本。撤销结算或切换正式正文时，旧流水保留并标记失效，再从当前初值和有效流水重算。
- 初始、卷末、重大修订、正文切换和手工节点可以冻结里程碑；数值语义映射发布为不可变版本，并可锁定提示词组件卡片版本。
- 客观事实、人物认知与读者认知使用不同对象。AI 知情提案自动入库但不自动确认，用户可修订、确认或驳回；任何历史位置查询都必须按叙事顺序裁切，未知时间不得推断。
- 完整故事时间由独立正本管理，章节和叙事顺序只记录讲述位置。AI 时间与事件关系先自动保存为版本化草案，人工确认后才生效；未知时间不得填充默认坐标，依赖旧正文的记录在切版时标陈旧但不删除。

## 依赖方向

```text
旧客户端路由/菜单 ──> @ai-novel/new-design/client
旧 Express 挂载点 ──> @ai-novel/new-design (Router)
                         │
                         ├─> new-design/domain
                         └─> new-design/database ──> PostgreSQL
```

箭头不能反向：`new-design/` 不允许导入 `client/src`、`server/src`、旧 Prisma 模型或旧业务 Service。未来删除旧客户端和旧服务端目录时，应能为新设计补充独立壳层，而不重写卡片领域与数据库代码。

## 运行时边界

- 默认只监听 `127.0.0.1`，使用非默认动态端口。
- 初始化密码随机生成，运行配置和数据库数据一起留在应用数据目录。
- 迁移只允许非破坏性前进；检测到不完整旧数据时停止并提示，不自动清空。
- Electron 打包必须把 PostgreSQL 原生目录解出 `app.asar`，并在打包验证中检查三个入口：`postgres.exe`、`initdb.exe`、`pg_ctl.exe`。
- CI 可通过 `NEW_DESIGN_DATABASE_URL` 接入真实 PostgreSQL，但不得切换到其他数据库实现。

## 当前信息架构

`/new-design` 只作为入口页；创作数据和结构定义分开：

```text
新设计
├─ 我的书籍
│  └─ 当前书籍：创作表单／多视图／本书资料库／本书字段
├─ 我的卡片
├─ 研究与分析
│  ├─ 市场雷达
│  ├─ 拆书
│  ├─ 研究记录
│  └─ 研究参考包
└─ 结构设计中心
   ├─ 元卡片类型
   ├─ 字典与关系
   ├─ 卡片组表单
   └─ 模板组
```

可以把它理解成“编辑部”和“印刷厂”分区：作者进入具体书籍写内容，结构设计者到印刷厂维护表格和模板。对应到路由：书籍页面必须携带真实 `bookId` 并读取书籍空间，结构中心只维护可复用定义。

> 🧠 **速记方法**：**写书进书里，造表进中心**。

> 🏠 **白话比喻**：六种视图像同一家医院里的挂号屏、医生病历和药房清单，看到的是同一位患者的不同切面，不能各自抄一份病历。对应到系统里：页面只保存怎么排列，事实、时间、关系与正文位置各回到唯一的后端对象。

> 🧠 **速记方法**：**一事实、多窗口；改一处、处处见**。

> 🏠 **白话比喻**：研究区像编辑部的资料室，榜单截图、原文、分析报告和正式书稿分柜保存。对应到系统里：扫描只收集公开来源，AI 分析另起运行版本，候选结论还要经过作者确认才进入卡片或开书输入。

> 🧠 **速记方法**：**先采集、再分析、后采用**；三步之间不自动越级。

市场雷达参考旧项目已经验证的 8 个公开榜单适配器与证据分层经验，但不导入旧服务作为运行时依赖。`new_book` 与 `new_author` 属于主要证据，默认用于判断近期入场机会；阅读、畅销、月票、月度和季度榜属于辅助证据，只验证持续需求和拥挤程度。每条送入 AI 的样本必须携带平台、榜单名称和证据层级，避免模型把成熟头部榜误读成新书趋势。

> 🏠 **白话比喻**：新书榜像商场门口“本周新品”货架，成熟榜像长期畅销区。新品货架适合看最近谁刚进场，畅销区适合看什么一直有人买；把两排货混在一起，就会把老爆款误判成新趋势。对应到雷达里：主要证据判断近期机会，辅助证据只做旁证。

> 🧠 **速记方法**：**新品看机会，老榜验需求**。

> 🏠 **白话比喻**：拆书报告像质检员写的验货单，原文位置是货架坐标，候选是整改建议；只有负责人签收的建议才会进入正式生产单。对应到系统里：证据锚定 `research_document_versions`，候选锚定运行版本，作者采用后才写入卡片或资源。

> 🧠 **速记方法**：**报告可重跑，证据可回看，候选要签收，正式资料留来源**。

研究参考包采用“可编辑身份 + 不可变发布版本”。开书会话通过 `book_creation_research_selections` 保存直接选择的研究版本、参考包版本和当时编译出的完整预填快照；建书成功后再写入 `book_research_references`。预填合并只填空白字段，非空冲突不覆盖，确保后续重新分析或发布参考包新版本不会改变已经确认的开书输入。

> 🏠 **白话比喻**：参考包像标了 v1、v2 的资料档案袋，开书时登记的是“拿了哪一只袋子”，而不是只记档案柜名字。对应到系统里：会话和书籍都引用精确版本并留快照，档案柜以后放入 v3 也不会换掉旧书使用的材料。

> 🧠 **速记方法**：**包可续版，书只锁版；空栏可补，旧字不擦**。

章节正文不直接覆盖章节卡字段，而由 `chapter_documents` 保存稳定身份与唯一正式版本指针。每次人工保存、AI 生成、修订或导入都向 `chapter_body_versions` 追加完整正文和内容哈希；采用操作在事务中校验章节修订号，更新指针并写 `chapter_body_adoptions`。`chapter_text_anchors` 永久绑定产生它的正文版本，当前指针变化只改变陈旧判断，不改写历史坐标。

> 🏠 **白话比喻**：章节卡像书的目录条目，正文版本像编辑部编号存档的校样，正式指针像“准印版”印章。对应到系统里：目录不会塞入反复覆盖的正文，候选校样也不能自己抢到印章。

> 🧠 **速记方法**：**卡管章节名，档案管顺序，版本管正文，指针管采用**。

`canonical_facts` 是确认事实的唯一正本，卡片字段继续承载用户友好的资料描述。事实创建固定为提案，证据通过 `canonical_fact_evidence` 指向正文锚点、卡片版本或研究证据；值冲突写入独立冲突表，不以最后写入者覆盖。更正通过新事实的 `supersedes_fact_id` 建链，人工确认后旧事实才转为被取代。章节正文采用指针改变时，证据陈旧状态在同一事务内刷新，未确认提案标陈旧但不删除。

> 🏠 **白话比喻**：卡片像公司通讯录里的个人备注，事实库像人事系统里的已审核记录。对应到系统里：备注可以帮助理解，但工资、岗位、归属等正式结论必须有来源、审核和更正单，不能靠谁最后改了一段文字决定。

> 🧠 **速记方法**：**卡片方便看，事实负责真；AI 只提议，人来盖章**。

状态内核采用“流水正本 + 当前投影”：`entity_initial_state_versions` 和 `state_changes` 保存不可变来源，`chapter_settlements` 保存用户确认边界，`current_state_projections` 只负责快速读取。正文采用操作在同一事务中传播结算失效并创建切版里程碑，避免后续章节继续读取已经撤回的状态。

> 🏠 **白话比喻**：这像会计总账和余额表。每笔收入支出是不能偷偷改掉的总账，余额表是按有效账目算出的当前结果；作废凭证后重新汇总即可。对应到系统里：变化历史不删，投影可以重建。

> 🧠 **速记方法**：**流水是真，投影是算；换稿作废，重算不断档**。

人物和读者认知采用“命题 + 持有者 + 版本化提案 + 确认流水”模型。`epistemic_claims` 只描述被相信的内容，不替代 `canonical_facts`；`knowledge_state_proposals` 将 AI 输出立即保存为可编辑草案，`knowledge_state_proposal_versions` 留住每次修改，用户确认后才追加 `knowledge_state_changes`。人物与读者使用不同持有者键，按历史叙事位置读取时只返回当时已经生效且时间明确的记录。正文采用指针改变时，旧版本上的认知流水标记失效并重建当前投影，不删除审计链。

> 🏠 **白话比喻**：侦探小说里，警方掌握的真相、嫌疑人自己的误判、读者已经看到的线索不会同步更新。对应到系统里：客观事实、每个人物的认知和读者认知分开记账，才能写出可信的信息差而不提前剧透。

> 🧠 **速记方法**：**事实管真，认知管信；AI 先落草稿，人确认生效；回到第三章，只翻第三章以前的页**。

完整故事时间采用“事件时间正本 + 叙事出现 + 版本化关系”边界。`story_event_timings` 只回答事件在故事世界中何时发生，支持绝对时刻、自定义历法、相对事件、部分未知和完全未知；`story_event_narrative_occurrences` 只回答作者在哪一章、场景或正文锚点讲述它。旧 `story_time_positions` 作为当前事件视图的兼容投影，通过正式时间 ID 回指正本，不允许反过来成为第二份来源。

时间和关系写入都使用提案链。AI 创建提案时立即持久化不可变初版，用户采用前的修改继续追加版本；确认操作重新校验修订号，以及人工、当前正文锚点、已确认事实、状态提案或上游计划版本来源。计划转实际通过新时间记录替换原计划，原记录保留。正文切版会把依赖旧稿的有效时间、时序、因果和叙事出现标为陈旧，不能在换回旧稿时自动复活。

事件关系分成两个集合：`before / after / simultaneous / overlaps / contains` 只表达先后与范围，`causes / enables / blocks / depends_on` 才表达因果或依赖。查询层分别提供时间范围、叙事章节、并发事件、时间邻居和因果上下游；没有可比较坐标的未知时间不会为了排序被推断成 0。

> 🏠 **白话比喻**：历史事件发生在一个日期，但教科书可以在不同章节反复讲它；“同时发生”也不等于“彼此导致”。对应到系统里：世界时间、讲述章节、时序关系和因果关系是四张互相引用但不能混写的表。

> 🧠 **速记方法**：**何时发生看时间，何处讲述看章节；挨着不等于导致，未知绝不塞进队首**。

## 后续边界

关系图可视化、AGE、pgvector 和旧数据迁移仍属于后续阶段，不在当前菜单放置占位入口；旧小说菜单、页面和 SQLite 继续保持不变。

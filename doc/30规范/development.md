# 新版写作底座开发规范

## 适用范围与优先级

适用于 `new-design/` 的产品、源码、文档和交付协作。仓库 [AGENTS.md](../../AGENTS.md) 的安全、AI-first、用户体验、分支、Prompt 和发布要求是强制规则；本篇只给新版工作的定位和执行口径，不放宽或复制全部硬约束。具体命令与环境以[独立开发与运行](../../new-design/docs/standalone-development.md)、当前锁文件和实际机器配置核对。

## 开工与证据

1. 明确本次目标、不做项、必须保持的旧书数据／页面／接口行为及验收范围。按已有入口定向查文档和源码；有调用、数据或配置依赖再补上下游，不全量重审无关模块。
2. 区分已确认产品目标、现有设计、源码声明、当前环境启用和实际运行结果。旧版功能、历史检查点和测试桩均不能代替新版的运行证据；已覆盖且未被修改推翻的有效检查可以复用。
3. 尊重当前工作区其他人的修改。小范围用精确补丁；改动数据、迁移、模型、运行任务或恢复时先确认影响与保护措施。删除或重置业务数据须符合 [AGENTS.md](../../AGENTS.md) 的备份和明确批准门禁。

## 实现约束

- 写作意图、路由、规划与推荐以 AI 结构化理解为主；固定判断只承担输入校验、安全约束和结构化结果后的确定性处理。新增能力先扩展任务合同、输出结构或工具约定，不堆关键词分支。
- 作者资料、正文候选、正式采用、事实状态和任务账本各有正本；页面和后台统一经过专业命令。幂等键、版本、权限、失败回执和恢复位置需与写入边界一起设计，不能靠 UI 隐藏按钮保证正确性。
- 保持 `new-design/` 独立的页面、服务、模型和 PostgreSQL 边界；不能为省事导入旧版业务 Service、旧 Prisma/SQLite 或旧模型配置。具体新增依赖、全局版本切换与环境安装不由本篇授权。
- 数据库变更先核[数据库架构](../20架构/database.md)和目标 SQL：普通迁移与手动迁移分别维护清单，补齐数据字典与受影响业务合同；目标库是否已安装须看实际迁移记录。启动可能应用普通迁移，备份、恢复和破坏性步骤遵守项目授权与数据保护门禁。
- 面向新手的界面写“能做什么、下一步和影响”，隐藏实现术语；“运行记录”只读，重试、采用与恢复返回原业务页面。既有页面参考的复刻范围和低边框视觉规则见 [AGENTS.md](../../AGENTS.md)。
- 重构以业务职责、对外门面和依赖方向为准；不为文件行数单独拆碎模块。Prompt、运行合同、章节生产链和跨模块状态变更须更新其唯一长期知识页。

## 检查与交付

- 编码检查按影响和项目节点进行。代码变更就绪后优先选择相关模块的类型检查、边界检查或针对性测试；跨模块运行合同按风险补构建和必要的真实数据库／模型证据。文档改动只核链接、范围、术语、差异及 Git diff，不默认启动服务或跑全仓构建。
- 页面视觉与浏览器人工验收默认交给用户；不能据此声称已经完成 UI 验收。功能实现、静态检查、环境启用、真实运行与用户验收分别报告。
- 新的长期规则原位更新 `docs/wiki/` 或对应 `new-design/docs/` 专题；`doc/` 只维护跨主题入口与稳定基线。执行状态留任务工具或既有阶段入口，用户可见变化进发布说明，历史交 Git，不造同主题日期副本。
- 提交前只暂存本次文件，检查差异和链接；是否需要更新发行说明依仓库规则按用户可见影响判断。分支、`beta` 集成、发布与数据操作各有独立门禁，文档写入不授予推送、合并或部署权限。

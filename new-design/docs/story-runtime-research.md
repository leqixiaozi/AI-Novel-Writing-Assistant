# Story Runtime 研究与新版适配判断

## 范围与证据

本文提炼作者提供的《AI 小说 Story OS 改造任务说明》，用于判断哪些想法适合 `new-design/`。材料提出的是目标和研究线索，不是已批准的迁移清单、表结构、开发顺序或验收结果。本次仅对新版文档、源码入口和外部仓库公开说明做静态研究；未连接作者数据库、运行服务或模型，也未验证长篇实际效果。

新版与旧版是分开的底层系统。旧版页面可供对标，旧版业务代码只读，新版业务不能调用旧版。新版以卡片与版本承载资料，以各领域的候选、采用和结算记录维护正式结果；不能照材料中的概念对象逐项新建表。现有边界见[架构总览](../../doc/20架构/overview.md)和[数据模型](data-model.md)。

## 值得保留的设计意图

1. **长期连贯优先于一次生成**：目标是让长篇在章节换稿、角色认知变化、时间和因果变化后仍能追溯有效来源，而不是只靠扩大提示词。几十万至百万字是材料提出的目标规模，尚无本项目性能或质量验证。
2. **分开创作职责**：导演决定推进方向，角色模拟提出角色视角下的行动，世界约束裁决可发生的后果，写作环节形成正文，审核与领域命令处理候选和正式采用。这是职责草图，不要求为每个职责建立独立 Agent 或模型调用。
3. **候选与正本分界**：模型产生的正文、事实、认知、状态和修订建议先保存为可追溯候选；只有所属领域的明确采用／结算才能改变正式状态。任何审稿结论也须绑定它实际审过的内容版本。
4. **上下文有合法范围和解释**：任务应读取该书、该叙事位置、该角色可知的有效来源，并记录确切版本、入选原因和预算。RAG 负责找候选材料；PostgreSQL 关系正本裁决事实，AGE 与 pgvector 只承担可重建的查询／检索投影。
5. **修订之后能定位影响**：正文、计划、事实或状态变更须使依赖旧版本的结论显式陈旧，迟到结果不得覆盖新版本。质量问题与数据完整性失败应分账，避免局部写作问题直接停掉全书。

## 与新版现状的对应

以下“已有基础”仅指文档及源码静态可见的合同；不表示作者环境已安装、功能已启用或端到端验收。

| 材料中的概念 | 新版已有基础 | 仍需研究的差距 |
| --- | --- | --- |
| Canon Event Ledger、Candidate → Canon | `canonical_facts`、状态／知情变化流水、`chapter_adoption_sessions`、`chapter_stable_checkpoints` 和章节结算事件已分领域保存证据与正式结果；下一章读取稳定检查点。[采用结算](chapter-adoption-settlement.md) | 是否需要一个**只读聚合**，按章／场景解释“发生了什么、谁知道什么、何时生效”，先核现有视图与查询；不能先造第二套正本。 |
| Character Knowledge State | `epistemic_claims` 与人物／读者持有者的知识提案、正式流水和当前投影已分离客观事实、相信、怀疑、误解与未知。[数据模型](data-model.md#人物读者知情与误解状态) | 核实实际生成和角色模拟是否始终按目标叙事位置消费相应持有者的有效记录，特别是角色私有知识和未来信息隔离。 |
| Scene Contract | 场景卡与故事→卷→章→场景的规划版本、精确规划引用已存在；章节生成读取已采用且未陈旧的场景内容。[数据模型](data-model.md#故事卷章场景规划版本)、[章节生产模块](../src/server/database/chapterProduction/README.md) | 材料要求场景成为最小执行单位，并冻结入场／离场状态、POV、禁行事件与知识边界。当前可确认的是场景规划被章节任务消费，不能据此认定有独立场景执行、逐场裁决和结算合同。需先判定是否值得改变现有章节级生产链。 |
| Context Compiler | 版本化 `context_bindings`、预览、不可变 `context_manifests` 已记录确切来源、入选／排除原因、优先级和预算；章节生产会冻结连续性来源。[上下文组装](context-management-and-assembly.md)、[章节生产模块](../src/server/database/chapterProduction/README.md) | 是否所有拟议职责能共用同一合法上下文投影仍未证明；“统一服务”是接口边界问题，不等于重建一套上下文数据库。 |
| Revision ID + Hash | 规划和正文版本有内容哈希；AI 尝试、上下文清单、质量报告和依赖账本锁定来源版本或输入哈希；章节迟到回执有拒绝路径。[数据模型](data-model.md#ai-执行合同上下文清单与模型路由快照)、[章节工作台](chapter-writing-workspace.md) | 对材料拟议的多阶段角色模拟、裁决、写作、审稿，尚无“同一场景修订＋正文哈希”贯穿全链的证明。先画出阶段间实际输入／输出契约，再判断新增身份字段是否必要。 |
| State Delta、停滞判断 | `state_change_proposals`、`state_changes`、知识变化和轻量生命周期已能记录变化；质量账本可以登记局部问题。[数据模型](data-model.md#可配置状态章节结算与投影) | “连续若干场几乎无变化＝停滞”尚只是材料中的诊断假设。要定义叙事推进指标及误报处理，不能用硬编码阈值自动改写 AI 决策或把局部质量债升级为全书失败。 |
| Revision Cascade、因果图 | `dependency_resources/edges`、失效和重算回执负责精确版本影响；时间／因果记录是关系正本，AGE 是查询投影；旧章换稿已有影响预览和后文人工复核。[数据模型](data-model.md#统一依赖失效传播与重算账本)、[旧章换稿](chapter-revision-recompute.md) | 材料中的跨场景因果模拟、分支世界线未由现有依赖图直接证明；依赖关系也不能直接当作剧情因果。 |
| Auto Director、Character Simulation、World Arbiter | 新版导演按已采用计划编排章节任务；书内人物对话是非事实沙盒；世界一致性能力负责检查和修复草稿。[导演模块](../src/server/application/productionDirector/README.md)、[人物对话边界](wiki/character-dialogue-boundary.md)、[世界一致性模块](../src/server/application/worldConsistency/README.md) | 三者尚未组成材料中的逐场“独立角色决策→行动冲突→世界裁决→故事节拍”执行链。现有沙盒和检查结果不能冒充已发生的正式故事事件。 |
| Skill Runtime、Literary Engine、Cold Reader | 已有写法／质量资源卡、受控 PromptAsset、配方／任务合同、章节质量账本及多维视图。[数据模型](data-model.md#ai-执行合同上下文清单与模型路由快照)、[多维视图](multiview-quality-workspace.md) | 动态技能选择、风格指纹与漂移测量、带连续状态账本的冷读协议尚无闭环证据。先验证对应创作问题和现有资源能否承载，再决定是否扩展合同。 |

## 适配边界与待定设计

- **场景级运行粒度**：材料把 Scene 设为最小运行单位；新版当前正文、采用、稳定检查点以章为关键边界。若以后引入逐场执行，须先说明场景结果如何汇入一章的唯一正式正文和结算，不能让场景表成为平行正文正本。
- **自动化与作者确认**：初学者需要默认建议和自动推进，但重要事实、认知、状态与正文的正式采用仍按现有领域策略和人工确认合同处理。材料所称 Validator 不能绕过这些边界。
- **质量与安全门禁**：LLM 可作主观写作判断；程序可做结构化输出校验、来源版本与数据安全验证。按仓库 `AGENTS.md`，局部质量债默认随章节继续，只有明确重规划、质量优先人工暂停、无可用正文或安全／数据完整性失败才进入相应停顿。不得把“每章 Judge PASS”直接改成全书硬门槛。
- **表与投影**：材料的 `scene_revision`、`character_knowledge`、`narrative_debt` 等名称是概念示意，不是迁移要求。先复用既有卡片、规划、正文、事实、状态、知情、依赖与质量记录，只有证明现有正本无法表达的新语义才评估结构变化。AGE、pgvector 不写正式事实。
- **阶段排序**：原材料的 Phase 1–5 是提议，不覆盖本项目正在执行的新版对标计划或手动迁移门禁。1–3 章滚动窗口、30／50／100 章测试、世界线分支和固定风格分数均需另行验证成本、收益及现有链路影响。

## 外部参照的取用结论

只把外部项目作为设计参照，不引入其代码、运行栈、依赖或许可证义务。对照的是公开仓库说明，未独立执行其项目：

| 来源 | 可借鉴的具体问题 | 对新版的判断 |
| --- | --- | --- |
| [novel-studio](https://github.com/Xiaoyangy/novel-studio) | 它公开描述先进行角色／世界推演、冻结有限章节窗口、再写作与审核，并给各阶段绑定来源 digest 与正文 SHA。 | 可研究“冻结来源、迟到拒绝、角色所知边界”；其至多三章窗口是该项目做法，不直接作为新版参数。 |
| [AeonEchoes](https://github.com/NekoStash/AeonEchoes) | 仓库公开定位包含版本化 Story Bible、章节版本、叙事图与多角色写作工作流。 | 可对照对象版本和连续性呈现；公开定位不足以证明它的事务或长篇质量效果。 |
| [fiction-forge](https://github.com/geobond13/fiction-forge) | 仓库提供带状态台账的冷读协议、上下文服务和风格／重复扫描，并说明扫描器适合作回归检查。 | 可研究“读者连续性检查”与“风格测量”；不能把模式扫描命中率当作小说质量总分。 |
| [agent-skills](https://github.com/jwynia/agent-skills) | 仓库将创作技能按叙事任务组织。 | 可用来整理写作方法分类；是否需要运行时技能选择，要先与现有资源卡和任务合同对齐。 |
| [stylometric-transfer](https://github.com/ngpepin/stylometric-transfer)、[humanizer-zh](https://github.com/ai-zixun/humanizer-zh) | 前者公开提供可检查的风格指纹、改写和偏差报告；后者是中文润色／去模板化技能。 | 仅作为文学编辑研究线索；任何仿写或改写都应保留事实、来源与作者最终采用权。 |

材料还提及 `danjdewhurst/story-skills`、SillyTavern、Calliope／Manuscript Reviser 等；本次没有逐项核实其具体实现与适用性，不能据材料描述推断新版缺口或直接移植。

## 下一步研究问题

1. 选一条真实的新版“场景规划→章节生成→候选→采用→稳定→下一章”路径，逐阶段核对确切版本、哈希、角色知识位置、失败与迟到回执，确认上表的合同是否在运行中接通。
2. 以一章内多场景和旧章换稿为样例，比较现有章节级结算与拟议逐场合同，明确新增运行粒度带来的作者操作、数据和恢复成本。
3. 从正式变化流水和质量问题中研究可解释的“故事推进／停滞”观察值，先作为诊断信息评估误报，再考虑是否交给 AI 导演使用。
4. 研究角色模拟和世界裁决的输入／输出最小合同：私有知识、行动提案、冲突后果、世界约束、正式采用各归哪个已有领域；未确认结果不得进入下一章正本。
5. 若要宣称支持超长篇，另定有代表性的作品、模型预算和质量评估口径，验证 30／50／100 章或更长运行的连续性、恢复与成本；静态结构不能证明该目标已达成。

这些问题是研究入口，不构成编码、迁移、模型运行或产品阶段启动授权。
